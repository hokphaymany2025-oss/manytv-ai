### ~~BUG-6 (P1) — `JobStore`'s single SQLite connection is not safe under real concurrent access~~ — FOUND & FIXED 2026-07-17

`backend/core/job_store.py`'s module docstring claimed "one long-lived connection in WAL mode needs no extra locking," reasoning that there's "only ever one writer... plus occasional readers." That assumption broke the moment something could issue truly concurrent reads: every public method wraps its sync `sqlite3` call in `asyncio.to_thread`, which dispatches to Python's real thread pool — two calls landing on two different OS threads at the same moment is exactly what a frontend polling several jobs' `GET /api/jobs/{id}` at once produces. `sqlite3.connect(..., check_same_thread=False)` only disables Python's same-thread *check*; it does not make the single shared `Connection` object safe for concurrent use from multiple threads at once. WAL mode is unrelated to this — it governs crash-safety/reader-writer isolation at the file level, not in-process thread-safety of one Python object.
- **How it was found:** not by code review or the 71 mocked tests (none of which exercise true OS-thread concurrency) — it surfaced live, the first time this project had a real client (the new frontend) polling multiple jobs concurrently. Manifested in the browser console as `Access to fetch ... has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present`, which was initially (and incorrectly) suspected to be a CORS misconfiguration — the backend log told the real story: `sqlite3.InterfaceError: bad parameter or other API misuse`, a 500 that (for reasons not fully root-caused, plausibly a raw connection reset bypassing normal header-adding middleware) Chromium reported using its generic cross-origin failure message instead of surfacing the actual 500.
- **Fix applied:** `JobStore.__init__` now holds a `threading.Lock`; the one choke point every public method already funnels through (`_run()`) wraps the actual sync call in that lock before dispatching to the thread pool, so only one thread ever touches `self._conn` at a time. Minimal, single-point fix — no changes needed to any of the individual `_*_sync` methods.
- **Verified by:** new `tests/test_job_store.py::test_concurrent_access_does_not_raise_sqlite_interface_error` (200 concurrent operations across a batch of jobs via `asyncio.gather`) — confirmed this test reliably reproduces the exact real error on every run when the lock is removed (3/3 attempts), and passes cleanly with the fix. Live-reverified: killed and restarted the real backend with the fix, re-ran the same Playwright browser session that had shown the CORS-shaped errors, got zero console errors on both a full run and a repeat.
